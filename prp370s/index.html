Section B · Agile portfolio of evidence

Digital Payment Solution · PayTrader

Project focus: a browser-based concept to help informal traders record and demonstrate cashless payments. Payment activity shown in a prototype should be described as simulated unless a live payment gateway has genuinely been integrated and tested.

Agile Team Charter

Shared purpose
Explore and prototype a practical digital payment workflow that can help informal traders keep clearer records of customer transactions.

Working principles

  • Keep user needs and project scope visible.
  • Break work into small, testable stories with clear acceptance criteria.
  • Use Trello to record priorities, ownership, status, decisions and blockers.
  • Mark work complete only when the agreed criteria and supporting evidence are available.
  • Communicate respectfully, review each other's work and raise risks early.
  • Do not describe simulated payments as real financial settlement.

User Stories and Tasks

These are project-specific story drafts to verify with the team and the current prototype. Keep only stories the team has accepted; attach screenshots of the actual Trello cards and their checklists.

Draft story · Trader

Record a transaction

As an informal trader, I want to record a customer transaction, so that I can keep a clear record of sales.

Possible acceptance criteria

  • Required transaction fields are validated.
  • A valid record appears in transaction history.
  • The record's status is clear and not presented as a real bank settlement unless verified.

Tasks: confirm fields, implement or verify form, validate inputs, test saved record, capture evidence.

Draft story · Customer

View payment instructions

As a customer, I want to see the trader's payment details or QR code, so that I can follow the intended payment process.

Possible acceptance criteria

  • Payment instructions are readable on mobile and desktop.
  • QR content, if present, matches the intended demo flow.
  • The interface clearly explains if payment is simulated.

Tasks: confirm flow, check QR/display, test responsive layout, review demo wording.

Draft story · Trader

Review transaction history

As an informal trader, I want to review previous transaction records, so that I can check what has been recorded.

Possible acceptance criteria

  • Saved transactions are listed with consistent details.
  • An empty state appears when no records exist.
  • Displayed statuses match the prototype's actual behaviour.

Tasks: verify list, check empty state, validate record details, test refresh behaviour.

Draft story · Account holder

Access my account securely

As a registered user, I want to sign in and access the correct account area, so that my information is not exposed to other users.

Possible acceptance criteria

  • Invalid credentials are handled safely.
  • Protected pages require authentication if that feature exists.
  • Sign-out returns the user to a public or sign-in view.

Tasks: verify authentication scope, test valid/invalid sign-in, check access boundaries.

User Stories · Reflection

Well-written user stories explain who benefits from a feature and why it matters. Acceptance criteria make the story testable and help the team agree what evidence is needed. These story examples are proposed, not a claim that the team has already accepted or completed them. I should compare them with the actual board, refine the wording with teammates and keep the story, checklist, implementation evidence and test result linked.

Agile Logbook

A logbook should record what happened, when it happened, what was learned, what is blocked and what happens next. Use dated entries based on actual work rather than writing retrospective entries from memory without checking.

Entry template

Date and activity

Work completed: What did I personally do?

Evidence: Which card, commit, screenshot, document or test supports it?

Blocker: What prevented progress?

Learning: What did I learn or change?

Next action: What will I do next and by when?

Agile Logbook · Reflection

A dated logbook makes individual contribution and team decisions easier to trace. It also helps me explain why work changed, what delayed progress and how feedback affected the next step. I should record events close to when they happen, include links to evidence and distinguish completed work from work still in progress. If a feature is blocked by another task, the entry should name the dependency and a realistic next action rather than implying the feature was tested.
