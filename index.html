Project Overview and Team Charter

The project explores a browser-based digital payment workflow for informal traders, with a focus on clear payment instructions and transaction records. Unless the team has integrated and verified a live payment gateway, payments shown by the prototype must be described as simulated.

Team purpose and ways of working

  • Keep the trader's needs and project scope visible.
  • Break work into small stories with testable acceptance criteria.
  • Use Trello to track priority, owner, status, blockers and evidence.
  • Only mark tasks complete when the criteria are met and evidence exists.
  • Record decisions and raise dependencies early.

AGILE EVIDENCE · USER STORIES

User Stories and Tasks

Project-specific story drafts to reconcile with the actual Trello backlog.

Draft story 01 · Trader

Record a transaction

As an informal trader, I want to record a customer transaction so that I can keep a clear record of sales.

Possible acceptance criteria

  • Required fields are validated.
  • A valid record appears in transaction history.
  • The status is clear and does not imply real settlement unless verified.

Tasks: confirm fields, verify form, test validation and capture a real result.

Draft story 02 · Customer

View payment instructions

As a customer, I want to see the trader's payment details or QR code so that I can follow the intended payment process.

Possible acceptance criteria

  • Instructions are readable on desktop and mobile.
  • QR content, if implemented, matches the demo flow.
  • Simulated payment is clearly labelled.

Tasks: verify the journey, check display and review mobile layout.

Draft story 03 · Trader

Review transaction history

As an informal trader, I want to review previous transaction records so that I can check what has been recorded.

Possible acceptance criteria

  • Records show consistent details.
  • An empty state is shown when there are no records.
  • Statuses match actual prototype behaviour.

Tasks: test the list, empty state, record details and refresh behaviour.

Draft story 04 · Account holder

Access my account securely

As a registered user, I want to sign in and access the correct account area so that my information is not exposed to other users.

Possible acceptance criteria

  • Invalid credentials are handled safely.
  • Protected pages require authentication where implemented.
  • Sign-out returns the user to a public or sign-in view.

Tasks: verify the authentication scope and test valid/invalid access.

User Stories and Tasks · Reflection

User stories connect a feature to the person who needs it and the value it should provide. Acceptance criteria make the expected behaviour testable and help the team decide what evidence is needed. These are draft examples rather than claims that the team has already accepted or completed the work. I should compare them with the real board, keep the team's agreed wording and link each story to its checklist, test result and implementation evidence.

Evidence to add: Screenshot of the actual Trello story cards, checklists, priorities and current statuses. Replace draft stories with the team's accepted stories.
